# ADR-0001: データ保存先・認証基盤に Supabase を採用する

**ステータス**: Accepted
**日付**: 2026-06-01
**関連Issue**: #10

## 背景（Context）

Phase 1 では localStorage のみでエントリーを保存していた。これは「まず動く夢日記を最速で作る」MVP 方針には合っていたが、以下の限界がある。

- **デバイス間で共有できない**：スマホで書いた記録を PC で見られない。FloatNote の主用途は「ベッドで片手スマホ操作」だが、振り返りは別デバイスでもしたい。
- **消失リスク**：ブラウザのキャッシュ削除・ストレージ上限・端末買い替えでデータが消える。夢やアイデアは「書いた瞬間にしか思い出せない」性質上、消失の痛みが大きい。
- **ユーザー分離ができない**：複数人が各自のアカウントで使う想定だが、localStorage は端末・ブラウザ単位でしか分けられない。

Phase 2 のゴールは「データをクラウドに移し、複数デバイス・複数ユーザーで安全に使えるようにする」こと。そのためには **データベース + 認証 + 行レベルのアクセス制御** が必要になる。

## 決定（Decision）

データ保存先と認証基盤に **Supabase**（PostgreSQL + Supabase Auth + Row Level Security）を採用する。

- データベース: Supabase の PostgreSQL（`entries` テーブル）
- 認証: Supabase Auth の **Google OAuth**
- アクセス制御: **Row Level Security (RLS)** で「自分の `user_id` の行だけ読み書き可能」を強制する
- クライアント: `@supabase/supabase-js` をフロントエンドから直接利用

## 理由（Rationale）

- **DB・認証・認可がワンセット**：DB を建てる／OAuth を実装する／アクセス制御をかける、を別々のサービスで組むより、Supabase 1 つで完結する方が個人開発の MVP として速い。
- **無料枠で十分**：ごく少人数（2人程度）・小さなテキストデータなので、無料枠（DB 容量・MAU）で運用できる。
- **RLS でセキュリティをDB層に寄せられる**：anon key はフロントに露出する前提のキーだが、RLS を有効化すれば「他人の行は SQL レベルで触れない」ことを DB が保証する。アプリ側のバグでデータが漏れる事故を構造的に防げる。
- **localStorage からの移行が素直**：Phase 1 のデータモデル（`id` を UUID、`entryDate` を `YYYY-MM-DD` 文字列で保持）は、そのまま Supabase のカラムにマッピングできるよう設計済み。`id` は localStorage の UUID をそのまま primary key に使える。
- **PostgreSQL という枯れた基盤**：将来検索・集計（Phase 3）に発展させても素の SQL で対応できる。ロックインの懸念が比較的小さい。
- **Vercel との相性**：実用デプロイ先に想定している Vercel と組み合わせる事例が豊富で、環境変数による鍵管理の作法も確立している。

## 検討した代替案（Alternatives）

- **Firebase (Firestore + Auth)**
  - 同じく DB + 認証ワンセット。却下理由：データモデルが NoSQL ドキュメント型で、Phase 1 の「配列を `entryDate` で filter する」素朴なリレーショナル設計と相性が悪い。SQL の知識がそのまま活きる Supabase を優先した。
- **自前バックエンド（Express/Hono + 任意のDB + 自前JWT認証）**
  - 最も自由度が高い。却下理由：認証・認可・DB 接続・デプロイをすべて自前で組むのは MVP の工数として過剰。「実際に使えるプロダクトを最速で」という方針に反する。
- **localStorage のまま継続 + 手動JSONバックアップ**
  - 却下理由：デバイス間共有とユーザー分離という Phase 2 の中心要件を満たせない。JSON エクスポート自体は別途バックアップ手段として残す（#5）。

## 結果（Consequences）

**得られるもの**
- 複数デバイスからの同期、ユーザーごとのデータ分離、消失リスクの大幅低減。
- RLS により「自分のデータしか見えない」がDB層で保証される。

**トレードオフ・新たに発生する責務**
- **鍵管理の責務**：Supabase URL / anon key を `.env.local` で管理し、絶対にコミットしない運用が必要。`VITE_` プレフィックスを付けるキー（anon key）と付けないキー（将来の OpenAI 等のサーバー専用キー）を取り違えない。
- **RLS 設定漏れ = 全公開事故**：テーブル作成直後から RLS を有効化することを徹底する。RLS なしの anon key は「誰でも全行読み書き可能」を意味する。
- **オフライン非対応**：localStorage と違いネットワーク必須になる。MVP では許容するが、将来オフライン対応が要件化したらキャッシュ層を別途検討する。
- **ベンダー依存の発生**：Supabase 固有の Auth / RLS に依存する。ただし DB は素の PostgreSQL なので、最悪 DB だけは移送可能。
